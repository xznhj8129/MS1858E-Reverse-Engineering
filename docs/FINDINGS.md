# Findings — boot fix, OSD and blue-frame behaviour

Tested on a live MS1858E CVBS→HDMI board with a Raspberry Pi Pico
(MicroPython 1.29), 24C16 EEPROM, converter powered from its own USB supply.
The MS1858E reset pin is not accessible on this board.

## Recommended image

`firmware/noblue.bin` — the working image for this setup.

- Boot with VTX off: snow.
- Signal loss: snow; no persistent blue; no blue on drop or re-lock.
- Boot with VTX on: not tested / no boot-state handling.
- "NO SIGNAL" text remains over the snow (mask ROM).

## Experimental bootfix images

`bootfix_skipe67a_fixed.bin` (v1):

- adds a one-time boot unblank/blue-clear and skips `E67A(0x11)` on unlock;
- **blue-screens when booting with the VTX off**: the first `E67A(0x11)` is
  skipped, so the scaler is never initialized;
- works if the VTX is already on at boot.

A v2 used an `EC09` "scaler initialized" flag: it called `E67A(0x11)` on the
first unlock, then skipped it on later drops. That fixed VTX-off boot, but the
`EC09` write after `E67A(0x11)` delays the `EC01`/`EC00` update and leaves one
blue frame on re-lock. Plain `noblue` has no blue on re-lock and is simpler, so
v2 is not recommended for VTX-off boot either.

## What changed vs the older images

- `noblue.bin`: snow on loss, no persistent blue. The ROM OSD text remains.
  This is the recommended image.
- `noblue_skipe67a.bin` (original repo image): **did not reproduce the documented
  behaviour on this board.** It showed snow for about one second after loss,
  then blue + "NO SIGNAL". Its cave sets `EC00=0xFF` and jumps to `0x0082`,
  skipping the stock `EC01=0` / `EC00=E1F4` update at `0x0075`; the ROM then
  falls into its no-signal screen.

## Blue frame = E67A(0x11)

The one-frame blue on `E1F4` transitions is the ROM scaler reinit
`E67A(0x11)`.

- Skipping it on unlock removes the blue on loss.
- Skipping it on reacquisition leaves the scaler blue forever; it is
  mandatory there.
- Therefore one blue frame on reacquisition is the cost of the mandatory
  reinit.
- `0294` also sends `E67A(0xCC)` on a quality drop; that is a separate OSD/blue
  flash. Setting `0294` to `RET` removes it.

## Boot state fix

With the skip-on-unlock image, powering up with the VTX already on stayed blue
until a signal reset. The `012D` hook only writes `F8B9=0` on the no-signal
path, which does not run at boot while signal is present.

Fix: on the first valid-video frame (tracked with `EC07`), write `F8B9=0` and
`E2EA=1` once, then commit video. The boot cave is routed from the `0x00A4`
video path. This is a one-time write, not a per-frame write.

## OSD text is in the mask ROM

There is no "NO SIGNAL" string or font in the 2 KB EEPROM. `strings` on
`stock.bin` finds only `MSES8858SE`. The text is generated by the mask-ROM OSD
engine; the overlay only sends commands (`E67A`) and never contains the text.

Tried and did not remove the text:

- `0294 = RET` (removes the `E67A(0xCC)` blue flash only)
- `02FD = RET`
- `E67A(0x77)` from `0294`
- `E67A(0x77)` every frame at `0x008B`
- `E67A(0x77)` at the end of hook `0043`
- header `0x30` experiments

`AV NTSD` is also mask-ROM OSD: it is the detected input-standard indicator and
appears for several seconds on acquisition by design.

## Header 0x30

Must stay `0x01` on this chip:

| Value | Result |
|---|---|
| `0x00` | black screen |
| `0x01` | normal |
| `0x02` | black screen |
| `0x0E` | TV reports "incompatible video signal" (HDMI timing broken) |

The MS2107 mute-pattern map does not apply to MS1858E header byte `0x30`.

## Failed experiments (do not ship)

- Per-frame dropout counter in hook `0043` (`EC08`, then `EC02`): both broke the
  no-signal path — blue screen, no snow. The hook is timing/state-sensitive;
  adding per-frame work is not safe.
- No reinit at all (`0x0070 → 0x0075` always): blue forever on reacquisition.
- `F8B9 = 1`: blue latch on, video killed.
- Header `0x30` variants listed above.
- `E67A(0x77)` per frame at `0x008B`: blue on no-signal.

## ROM dump feasibility

The 8051 can read its own mask ROM with `MOVC A,@A+DPTR`, but the MS1858E has no
USB, UART, JTAG or documented debug port. Its `SCL` pin is an I²C **master
output**, so the unexplained I²C device at `0x40` is not the chip's slave port.
A dump would require a custom overlay plus an export channel (I²C master or
bit-banged serial into the EEPROM) and reset automation. This is a separate
project and was not pursued.
